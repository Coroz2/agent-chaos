# Agent Chaos v0.5 Specification

**Status:** Released

**Release:** `v0.5.0`

**Distribution:** `agent-chaos-runner==0.5.0`

This document is the authoritative contract for Agent Chaos v0.5. Released specifications are
immutable historical records. Changes are limited to clearly labeled factual corrections or
errata and must not introduce behavior that was not part of v0.5.

## Product contract

Agent Chaos v0.5 adds reproducible probability windows. One configured HTTP fault can use a seed
and probability to select matching-request occurrences inside one finite inclusive window. The
same scenario, seed, and recorder-ordered matching-request sequence selects the same operations on
every supported Python version and platform.

The execution model otherwise remains one subprocess workload, one HTTP dependency, zero or one
fault, the five released HTTP fault types, structured black-box evidence, and no LLM-based recovery
judgment. Probability windows repeat one fault configuration; they are not multi-fault campaigns.

## Compatibility contract

- Scenario and event envelopes remain `schema_version: 1`.
- Every scenario valid under v0.1 through v0.4 remains valid under v0.5.
- Probability windows are an additive schema-1 capability. Earlier binaries need not accept them.
- Existing event types and payloads remain exact. Selected operations repeat the existing
  `FAULT_INJECTED`, operation, and retry event families.
- Every v0.5 run writes a strict schema-3 report, including baselines and occurrence schedules.
- `agentchaos inspect` accepts strict schema-1, schema-2, and schema-3 reports without migration or
  rewriting. Schema-1 and schema-2 summaries remain byte-for-byte unchanged.
- Commands, artifact filenames, exit-code meanings, lifecycle behavior, and all fault wire behavior
  remain unchanged.
- Existing analyzer precedence and reason codes remain unchanged except for
  `TRIGGER_WINDOW_INCOMPLETE` and the probability-evidence consistency rules below.
- No production dependency or supported-platform change is introduced.

## Scenario contract

Every fault accepts either the released occurrence schedule forms or this probability form:

```yaml
fault:
  type: http_error
  target:
    method: GET
    path: /customer/*
  trigger:
    probability: 0.5
    seed: 10
    window:
      start_occurrence: 1
      end_occurrence: 5
  status_code: 503
```

Probability rules:

- `probability` is an unquoted numeric value greater than zero and at most one, with no more than
  six decimal places. Booleans, strings, non-finite values, and more precise values are invalid.
- `seed` is a non-boolean integer from zero through `18446744073709551615` inclusive.
- `start_occurrence` and `end_occurrence` are positive non-boolean integers. The window is
  inclusive and the start must not exceed the end.
- All probability fields are required. Unknown fields are rejected.
- `occurrence`, `occurrences`, and probability fields are mutually exclusive.
- The same contract applies to `http_latency`, `http_error`, `http_rate_limit`,
  `http_malformed_json`, and `http_disconnect`.

All other schema-1 validation remains strict and unchanged. A scenario contains at most one fault,
and the selected fault type, target, and parameters are identical at every injection.

## Selection algorithm

The configured fault retains one counter beginning at one. A request increments it only when it
matches the target method and path and reaches the existing injection-selection point. Query values
do not participate in target matching. Retries participate in counting and may themselves be
selected. Oversized requests rejected before injection selection do not participate.

Requests before `start_occurrence` and after `end_occurrence` are not selected. Each occurrence
inside the window is evaluated exactly once. Reaching the inclusive end completes the window;
later matching requests are forwarded normally unless ordinary proxy behavior prevents forwarding.

Selection uses this portable algorithm:

1. Normalize the configured probability to integer millionths.
2. Encode `agentchaos-probability-v1:<seed>:<occurrence>` as ASCII.
3. Compute its SHA-256 digest and interpret the full digest as an unsigned big-endian integer.
4. Compute `floor(probability_millionths * 2^256 / 1_000_000)`.
5. Select the occurrence exactly when the digest integer is below that threshold.

Probability `1` selects every occurrence in the window. For probability `0.5`, seed `10`, and
occurrences one through six, the selected occurrences are exactly two and four.

For concurrent matches, the recorder sequence of eligible `OPERATION_OBSERVED` events is the
authoritative occurrence order. Matching observation, retry registration, and selection assignment
remain serialized sufficiently to preserve it.

## Recovery and events

The v0.4 concurrency-safe FIFO recovery queues remain unchanged. Each fault-related failure creates
one recovery-evidence row, one successful linked retry resolves at most one row, and a selected retry
may create another independent failure. Fingerprints, attempts, evidence ordering, and recovery
latency retain their released meanings.

The schema-1 event envelope remains exact. No probability, seed, window, or occurrence field is
added to an event payload. Every selected operation emits the released sequence beginning with
`OPERATION_OBSERVED`, optional `RETRY_OBSERVED`, and `FAULT_INJECTED`, followed by the fault's
released terminal evidence. The analyzer derives trigger evidence from the scenario and ordered
event stream.

## Outcomes and reason codes

Results remain exclusively event-derived. Recorded run errors, missing workload completion,
interruption, timeout, and exit-code mismatch retain their existing precedence. After those checks:

- A baseline with the expected workload exit produces `PASSED / BASELINE_SUCCEEDED`.
- Probability evidence that contradicts the published selector or recorded operation order produces
  `FAILED / INTERNAL_ERROR`.
- A configured fault with no injections produces `FAILED / FAULT_NOT_TRIGGERED`, whether or not its
  window completed.
- A probability trigger with at least one injection but fewer evaluations than its window size
  produces `FAILED / TRIGGER_WINDOW_INCOMPLETE`, regardless of observed recovery.
- Existing occurrence schedules retain `FAULT_SCHEDULE_INCOMPLETE` behavior.
- A completed trigger with no fault-related failed operation produces
  `PASSED / FAULT_TOLERATED`.
- A completed trigger whose failures all resolve produces `RECOVERED / RECOVERY_OBSERVED`.
- A completed trigger with any unresolved failure produces `FAILED / RECOVERY_NOT_OBSERVED`.

Probability consistency requires the injected operation IDs and their occurrence ordinals to match
the expected selection sequence exactly. Missing, extra, reordered, or duplicate selections are
internal errors. Diagnostics contain only safe counts or general consistency descriptions.

## Schema-3 reports

All v0.5 reports use the released top-level identity, workload, metrics, timing, artifact,
diagnostic, and plural recovery fields. `faults_injected` remains the total number of
`FAULT_INJECTED` events. The schema-3 fault object contains `configured`, `type`, `injected`, and a
discriminated `trigger` object.

An occurrence schedule is represented as:

```json
{
  "configured": true,
  "type": "http_error",
  "injected": true,
  "trigger": {
    "kind": "occurrence_schedule",
    "scheduled_occurrences": [2, 4],
    "completed_occurrences": [2, 4],
    "completed": true
  }
}
```

A probability window is represented as:

```json
{
  "configured": true,
  "type": "http_error",
  "injected": true,
  "trigger": {
    "kind": "seeded_probability",
    "probability": 0.5,
    "seed": 10,
    "window": {
      "start_occurrence": 1,
      "end_occurrence": 5
    },
    "evaluated_occurrences": 5,
    "selected_occurrences": [2, 4],
    "completed": true
  }
}
```

- `evaluated_occurrences` counts the contiguous portion of the inclusive window reached during the
  run and cannot exceed the window size.
- `selected_occurrences` contains actual injected ordinals in increasing recorder order and lies
  within the evaluated portion of the window.
- `completed` is true exactly when the full schedule or probability window completed.
- `injected` is equivalent to whether the trigger contains any completed or selected occurrence.
- A baseline uses `configured: false`, `type: null`, `injected: false`, and `trigger: null`.
- For ordinary completed experiments, the top-level injection count, trigger selections, and
  deterministic hash result must agree. A higher-precedence execution failure or
  `FAILED / INTERNAL_ERROR` may preserve contradictory evidence so the failure remains inspectable.

The plural recovery object is unchanged from schema 2. Strict versions cannot mix nested shapes,
and unknown fields remain invalid.

## Inspection and summaries

`agentchaos inspect` remains read-only, accepts a run directory or direct report path, reads no
companion artifact, and exits zero for every structurally valid report regardless of result.

Schema-1 and schema-2 reports retain their exact released summaries. Schema-3 occurrence schedules
retain the schema-2 injection ratio. Schema-3 probability reports add:

```text
Window evaluations:    <evaluated>/<window-size>
Faults injected:       <selected-count>
Successful recoveries: <successful>/<required>
```

The existing result, reason, failed-operation, retry, duration, and report-path lines retain their
wording. Summaries never print seeds, operation IDs, evidence rows, scenarios, or event payloads.

## Examples

v0.5 adds two deterministic offline examples and retains all twelve v0.1 through v0.4 examples.

### `api_503_probability_recovery.yaml`

- Uses probability `0.5`, seed `10`, and window one through five.
- Two refresh cycles reach all five occurrences; occurrences two and four inject HTTP 503.
- Both failures receive separate successful retries.
- Expected result: `RECOVERED / RECOVERY_OBSERVED`; CLI exit zero.

### `api_503_probability_incomplete.yaml`

- Uses the same selector with one refresh cycle.
- Three occurrences are evaluated, occurrence two injects, and its retry succeeds.
- The recovered partial window still fails as `FAILED / TRIGGER_WINDOW_INCOMPLETE`; CLI exit one.

Both use loopback dependencies and require no external network access.

## Verification contract

Coverage must include strict probability validation for all fault types; legacy scenario parsing;
portable golden vectors; window boundaries; probability one; concurrency-safe recorder ordering;
retry selection; zero, partial, exact, and inconsistent evidence; tolerated, recovered, and
unrecovered outcomes; strict schema-3 validation; legacy inspection fixtures and exact summaries;
all fourteen offline examples; and absence of sensitive traffic from generated evidence.

The release must pass the locked quality gate on supported Linux and macOS/Python combinations and
the distribution verification suite without adding a production dependency.

## Explicit non-goals

v0.5 does not add wall-clock windows, unbounded sampling, generated seeds, replay commands,
multi-fault campaigns, per-occurrence parameters, multiple dependencies, non-HTTP adapters, remote
execution, new fault types, streaming protocols, semantic grading, report migration, new CLI
commands, or a public plugin API. All remaining v0.1 through v0.4 limitations continue unless
explicitly changed above.
