# Agent Chaos v0.2 Specification

**Status:** Approved

**Release:** `v0.2.0`

**Distribution:** `agent-chaos-runner==0.2.0`

## Product contract

Agent Chaos v0.2 deepens deterministic HTTP resilience testing and improves the usability of saved
run reports.

It adds:

- behavior-preserving modular HTTP fault execution;
- read-only inspection of schema-1 reports;
- deterministic HTTP 429 rate-limit injection;
- deterministic malformed-JSON response injection.

The v0.1 execution model remains unchanged: one subprocess workload, one HTTP dependency, zero or
one fault, occurrence-based triggering, structured evidence, and no LLM-based recovery judgment.

## Compatibility contract

- Scenario, event, and report envelopes remain `schema_version: 1`.
- Every scenario valid under v0.1 remains valid under v0.2 with the same observable behavior.
- The `http_latency` and `http_error` wire responses, triggering, events, outcomes, reports, and
  cleanup behavior remain unchanged.
- v0.2 adds fault discriminator values to the schema-1 fault union. A v0.1 binary is not required
  to accept scenarios or events containing those new values.
- v0.2 reads v0.1 reports without migration.
- `report.json` retains exactly the v0.1 field structure. No fields are added, removed, renamed,
  or reinterpreted.
- Existing event types and payload fields remain unchanged. New faults use existing event
  families.
- Existing reason codes, analyzer precedence, artifact names, CLI commands, and exit meanings
  remain unchanged.

## Scenario contract

All v0.1 validation rules continue to apply. Fault models remain strict discriminated mappings,
reject unknown fields, and cannot mix fault-specific fields.

### HTTP rate limit

```yaml
fault:
  type: http_rate_limit
  target:
    method: GET
    path: /customer/*
  trigger:
    occurrence: 2
  retry_after_seconds: 1
```

Contract:

- `type` is exactly `http_rate_limit`.
- `target` and `trigger` use the existing schema-1 contracts.
- `retry_after_seconds` is required and is a positive integer with no implicit default.
- Status is fixed at 429 and is not configurable.
- On the selected occurrence, the proxy does not contact the upstream.
- The response contains:
  - status `429`;
  - `Retry-After: <retry_after_seconds>`;
  - `X-Agent-Chaos-Fault: http_rate_limit`;
  - `Content-Type: application/json`;
  - the fixed JSON object `{"error":"rate limit injected by Agent Chaos"}`.
- HTTP-date `Retry-After` values and custom bodies, statuses, or headers are invalid and
  unsupported.

### Malformed JSON

```yaml
fault:
  type: http_malformed_json
  target:
    method: GET
    path: /customer/*
  trigger:
    occurrence: 2
```

Contract:

- `type` is exactly `http_malformed_json`; the shorter `malformed_json` spelling is not accepted.
- No fault-specific configuration fields are accepted.
- On the selected occurrence, the proxy does not contact the upstream.
- The response contains:
  - status `200`;
  - `X-Agent-Chaos-Fault: http_malformed_json`;
  - `Content-Type: application/json`;
  - the fixed UTF-8 bytes `{"error":"injected by Agent Chaos"`, which are invalid JSON because
    the closing brace is intentionally absent.
- Agent Chaos does not inspect, capture, or corrupt an upstream response to produce this fault.
- Arbitrary response bodies, statuses, and headers are not accepted.

## Modular HTTP fault execution

HTTP fault execution becomes an internal typed abstraction selected by validated fault type.

The common proxy path remains responsible for:

- request buffering and operation fingerprinting;
- target matching and concurrency-safe occurrence counting;
- ensuring the configured fault fires at most once;
- fault-operation and retry state;
- event ordering and recording;
- ordinary upstream forwarding and response-size limits.

Individual internal executors provide the fault parameters and perform one of three dispositions:

- delay and then forward;
- return a fixed synthetic response;
- abandon a delayed operation after retry or disconnect.

Executors cover `http_latency`, `http_error`, `http_rate_limit`, and `http_malformed_json`.
Dispatch must be exhaustive for the validated fault union; an unhandled type is an internal error
rather than an implicit pass-through.

This abstraction is private in v0.2. It is not a public plugin API, entry-point registry, or
compatibility commitment for third-party fault implementations. The refactor must preserve all
v0.1 externally observable behavior.

## Events, failures, and recovery

Both new faults retain the existing event envelope and event sequence:

1. `OPERATION_OBSERVED`
2. `FAULT_INJECTED`
3. `OPERATION_FAILED`
4. On a later fingerprint match, `OPERATION_OBSERVED` and `RETRY_OBSERVED`
5. If the retry receives a status below 400, `OPERATION_SUCCEEDED`

### Rate-limit payloads

`FAULT_INJECTED`:

```json
{
  "kind": "FAULT_INJECTED",
  "operation_id": "<uuid>",
  "fault_type": "http_rate_limit",
  "parameters": {
    "retry_after_seconds": 1
  }
}
```

`OPERATION_FAILED`:

```json
{
  "kind": "OPERATION_FAILED",
  "operation_id": "<uuid>",
  "fingerprint": "<sha256>",
  "failure_kind": "injected_http_rate_limit",
  "status_code": 429,
  "fault_related": true
}
```

### Malformed-JSON payloads

`FAULT_INJECTED`:

```json
{
  "kind": "FAULT_INJECTED",
  "operation_id": "<uuid>",
  "fault_type": "http_malformed_json",
  "parameters": {}
}
```

`OPERATION_FAILED`:

```json
{
  "kind": "OPERATION_FAILED",
  "operation_id": "<uuid>",
  "fingerprint": "<sha256>",
  "failure_kind": "injected_malformed_json",
  "status_code": 200,
  "fault_related": true
}
```

The 200 status records the injected HTTP response status; `failure_kind` records that the response
contract was deliberately malformed. This represents a deliberately invalid application payload
despite transport success. The same operation must not also emit `OPERATION_SUCCEEDED`.

Both faults use the existing deterministic fingerprint of uppercase method, concrete path, query
hash, and body hash.

### Outcome rules

Existing analyzer precedence remains authoritative.

For either new fault:

- Expected workload exit plus no injection: `FAILED / FAULT_NOT_TRIGGERED`.
- Expected workload exit plus injection but no successful fingerprint-matched retry:
  `FAILED / RECOVERY_NOT_OBSERVED`.
- Expected workload exit plus a linked retry that succeeds with status below 400:
  `RECOVERED / RECOVERY_OBSERVED`.
- Unexpected workload exit, timeout, interruption, setup error, or internal error retains its
  existing higher-precedence result and reason.
- `FAULT_TOLERATED` is not available for these synthetic response faults because the proxy records
  a fault-related failed operation.
- Recovery latency remains the elapsed time between the fault-related `OPERATION_FAILED` event and
  the linked retry's `OPERATION_SUCCEEDED` event.

Retry evidence remains a deterministic black-box heuristic. Agent Chaos does not infer whether a
workload respected `Retry-After`, successfully parsed content, achieved its semantic task, or
intended a request as a retry.

## Report inspection CLI

```text
agentchaos inspect <run-directory-or-report.json>
```

- A directory argument resolves to `<directory>/report.json`.
- A file argument is read as the report itself, without requiring a particular basename.
- Inspection strictly validates the existing schema-1 `Report` model, including rejection of
  unknown fields and unsupported schema versions.
- Inspection reads only `report.json`; it does not parse events, scenarios, or logs.
- It never runs a workload, starts a dependency, contacts the network, or creates, updates,
  repairs, or migrates artifacts.
- A valid report whose experiment result is `FAILED` still produces inspection exit code 0.

Inspection prints the same result summary as `run`. One shared renderer accepts a validated report
and resolved absolute report path so live and saved-run output cannot drift. The summary contains
only:

- result and reason code;
- injected-fault count;
- failed-operation count;
- retry count;
- whether successful recovery was observed;
- total duration;
- resolved report path.

Inspection never prints diagnostics, logs, event payloads, scenario content, or other artifact
contents.

Exit codes:

- `0`: a report was successfully validated and displayed, regardless of experiment result;
- `2`: invalid command usage, missing input, unreadable input, directory without `report.json`,
  malformed JSON, unsupported schema version, or report-schema validation failure;
- `3`: an unexpected internal inspection failure;
- `130`: interruption.

Existing `run`, `validate`, version, and help contracts remain unchanged.

## Reports and artifacts

- `report.json` remains strict `schema_version: 1`.
- New runs use `fault.type` values `http_rate_limit` or `http_malformed_json` without changing
  `FaultReport`.
- No new reason codes or report metrics are introduced.
- v0.1 and v0.2 reports are mutually compatible at the report-model level because `fault.type` is
  already a nullable string.
- Artifact filenames and relative references remain unchanged.
- `scenario.yaml` remains an exact copy of the supplied scenario for compatibility and
  reproducibility.
- Workload and managed-dependency logs remain verbatim subprocess output.

Safety requirements:

- Scenarios and subprocess output are user-authored inputs; users must not place secrets in
  scenario environment overrides, command arguments, or process output. Secrets should be
  supplied through inherited environment configuration.
- Agent Chaos-generated events, reports, diagnostics, and terminal lifecycle messages must not
  contain request or response headers, bodies, raw query values, environment values,
  authorization data, or URL user information.
- Framework-generated error messages must be reduced to safe phase-specific descriptions and
  exception types when raw exception text could contain URLs, credentials, or request data.
- Persisted HTTP evidence remains limited to the v0.1 safe fields and hashes.
- Synthetic fault bodies and headers are fixed by this specification and are never copied from
  dependency traffic.
- `inspect` displays only the shared result summary and never exposes diagnostics, logs, events,
  scenario content, or other artifact contents implicitly.

## Example scenarios

v0.2 adds three deterministic offline examples while retaining all four v0.1 examples unchanged.

### `api_429_recovery.yaml`

- Targets the second `GET /customer/*`.
- Uses `http_rate_limit` with `retry_after_seconds: 1`.
- The demo workload recognizes the 429, uses the integer `Retry-After` delay, retries the identical
  request, and exits 0.
- Expected result: `RECOVERED / RECOVERY_OBSERVED`.
- Expected CLI exit: 0.

### `http_malformed_json_recovery.yaml`

- Targets the second `GET /customer/*`.
- Uses `http_malformed_json`.
- The demo workload treats JSON decoding failure as retryable, retries the identical request,
  receives valid upstream JSON, and exits 0.
- Expected result: `RECOVERED / RECOVERY_OBSERVED`.
- Expected CLI exit: 0.

### `http_malformed_json_failure.yaml`

- Targets the second `GET /customer/*`.
- Uses `http_malformed_json` with the demo workload limited to one attempt.
- The workload exits with its configured expected exit code after the JSON decoding failure
  without making a retry.
- Expected result: `FAILED / RECOVERY_NOT_OBSERVED`.
- Expected CLI exit: 1.

Changes to the demo workload must not alter the results or exit codes of the existing baseline,
latency, 503-recovery, and 503-failure examples.

## Verification contract

Unit coverage must include:

- acceptance and rejection of each exact new YAML contract;
- required positive `retry_after_seconds`;
- rejection of mixed or unknown fault fields;
- preservation of all v0.1 scenario parsing and normalization;
- exhaustive internal executor dispatch;
- unchanged v0.1 HTTP error and latency wire behavior;
- exact 429 status, safe JSON, and required headers;
- exact malformed-JSON bytes, status, and headers;
- confirmation that synthetic faults do not contact upstream;
- occurrence counting and exactly-once injection under concurrency for every fault type;
- exact fault event parameters and failure kinds;
- absence of a duplicate success event for malformed JSON;
- recovered and unrecovered analyzer paths for both new faults;
- existing outcome-precedence rules;
- parsing of representative v0.1 and v0.2 reports;
- report shape equality with the v0.1 schema;
- identical shared summary rendering for `run` and `inspect`;
- `inspect` summary output from both a directory and direct report file for `PASSED`, `RECOVERED`,
  and `FAILED` reports;
- `inspect` exit codes for failed experiments, missing or unreadable reports, malformed JSON,
  unknown fields, unsupported schema versions, internal failures, and interruption;
- byte-for-byte preservation of every artifact during inspection;
- safety assertions that raw headers, bodies, queries, environment values, and unsafe exception
  text are absent from generated events and reports.

End-to-end coverage must include:

- all four existing v0.1 examples with unchanged results and exit codes;
- 429 recovery with one injection, one failed operation, a linked successful retry, and
  `RECOVERED`;
- malformed-JSON recovery with the same evidence chain;
- a no-retry case for each new fault producing `FAILED / RECOVERY_NOT_OBSERVED`;
- inspection of a newly produced successful report;
- inspection of a newly produced failed report returning exit 0;
- inspection of a retained v0.1 report fixture.

The release must pass the repository's full locked quality gate on supported Linux and
macOS/Python combinations without adding a production dependency.

## Explicit non-goals

v0.2 does not add:

- a public fault plugin or executor API;
- configurable synthetic response bodies, arbitrary headers, or alternative 429 statuses;
- HTTP-date or fractional `Retry-After` values;
- upstream response capture or mutation for malformed JSON;
- validation that a workload obeyed `Retry-After`;
- semantic JSON-consumption, task-success, or LLM-based recovery judgment;
- alternate inspection formats, event-stream querying, diagnostics or log viewing, report editing,
  migration, aggregation, or a browser UI;
- automatic redaction of arbitrary user-authored scenario arguments or subprocess output;
- connection resets, streaming faults, SSE, WebSockets, CONNECT, or TLS interception;
- multiple dependencies, multiple faults, schedules, windows, probabilistic triggers, suites, or
  campaigns;
- non-HTTP adapters, remote execution, or broader platform support.

All remaining v0.1 limitations continue unless explicitly changed above.
