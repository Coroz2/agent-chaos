# Agent Chaos v0.4 Specification

**Status:** Released

**Release:** `v0.4.0`

**Distribution:** `agent-chaos-runner==0.4.0`

This document is the authoritative contract for Agent Chaos v0.4. Released specifications are
immutable historical records. Changes are limited to clearly labeled factual corrections or
errata and must not introduce behavior that was not part of v0.4.

## Product contract

Agent Chaos v0.4 adds deterministic occurrence schedules and plural recovery evidence. One
configured HTTP fault can be injected at several selected matching-request occurrences, and the
result records recovery evidence for every fault-related failed operation rather than only the
first one.

The execution model otherwise remains focused: one subprocess workload, one HTTP dependency, zero
or one fault, the five released HTTP fault types, structured black-box evidence, and no LLM-based
recovery judgment. An occurrence schedule repeats one fault configuration; it is not a multi-fault
campaign.

## Compatibility contract

- Scenario and event envelopes remain `schema_version: 1`.
- Every scenario valid under v0.1, v0.2, or v0.3 remains valid under v0.4. A scalar
  `trigger.occurrence` is a one-entry schedule and retains its existing behavior.
- The new `trigger.occurrences` spelling is an additive schema-1 capability. Earlier binaries are
  not required to accept scenarios that use it.
- Existing event types and payload fields remain unchanged. Scheduled runs repeat the existing
  `FAULT_INJECTED`, operation, and retry event families.
- Every report produced by v0.4 uses `schema_version: 2`, including baseline runs and runs loaded
  from legacy scalar-occurrence scenarios. Earlier binaries are not required to read v2 reports.
- v0.4 `inspect` accepts strict v1 and v2 reports without migrating or rewriting either version.
  Its output for v1 reports remains byte-for-byte compatible with the v0.3 summary contract.
- Existing CLI commands, artifact filenames, exit-code meanings, workload and dependency
  lifecycle behavior, and the wire behavior of all five faults remain unchanged.
- Existing reason codes and analyzer precedence remain unchanged except for the new
  `FAULT_SCHEDULE_INCOMPLETE` reason and the plural recovery rules defined below.
- No production dependency or supported-platform change is introduced.

## Scenario contract

The scenario envelope remains schema 1. Every fault accepts exactly one of the two strict trigger
forms:

```yaml
fault:
  type: http_error
  target:
    method: GET
    path: /customer/*
  trigger:
    occurrences: [2, 4]
  status_code: 503
```

```yaml
trigger:
  occurrence: 2
```

Trigger rules:

- `occurrence` remains a positive integer.
- `occurrences` is a non-empty list of positive integers in strictly increasing order. Duplicate,
  zero, negative, boolean, fractional, unordered, and decreasing values are invalid.
- A one-element `occurrences` list is valid.
- `occurrence` and `occurrences` are mutually exclusive; specifying both or neither is invalid.
- Internally, scalar `occurrence: N` is treated as the schedule `[N]` without changing the exact
  supplied `scenario.yaml` artifact.
- The same trigger contract applies to `http_latency`, `http_error`, `http_rate_limit`,
  `http_malformed_json`, and `http_disconnect`.
- A schedule repeats the configured type, target, and fault-specific parameters at each selected
  occurrence. It does not accept per-occurrence fault types, targets, or parameters.

All other schema-1 validation and normalization rules remain unchanged. Fault models remain strict,
unknown fields are rejected, and a scenario still contains at most one fault.

## Schedule selection

The schedule counter is local to the one configured fault and begins at one. A request increments
it only when it satisfies the existing target method and path rules and reaches the existing
trigger-selection point. Query values do not participate in target matching. A later request that
is classified as a retry still participates in occurrence counting and can itself be selected for
injection.

For concurrent matching requests, occurrence order is the authoritative recorder sequence of the
eligible requests' `OPERATION_OBSERVED` events. The proxy must serialize matching observation and
schedule assignment sufficiently to preserve that order. The request at each configured ordinal
is selected exactly once; no request at an unconfigured ordinal is selected. Once the last
scheduled occurrence has been evaluated, later matches are forwarded normally unless ordinary
proxy behavior prevents forwarding.

Each scheduled injection independently uses the released wire behavior for its fault type. In
particular, synthetic-response and disconnect faults do not contact upstream, latency retains its
existing forwarding and abandonment rules, and every selected disconnect records durable failure
evidence before terminating the client connection.

## Retry correlation and recovery evidence

The proxy maintains concurrency-safe FIFO queues of unresolved fault-related failures, keyed by
the existing deterministic operation fingerprint. The fingerprint remains the SHA-256-derived
combination of uppercase method, concrete path, query hash, and body hash.

For each later operation with the same fingerprint:

1. if its queue is non-empty, `RETRY_OBSERVED` links the operation to the oldest unresolved failed
   operation;
2. the operation is then independently evaluated against the occurrence schedule, so it may also
   receive the configured fault;
3. a linked `OPERATION_SUCCEEDED` resolves only the failed operation named by that
   `RETRY_OBSERVED`; and
4. a linked operation that fails does not resolve the older failure, and any new fault-related
   failure is appended to the same queue.

A successful operation can resolve at most one failure. A failure leaves the FIFO only after a
linked operation succeeds. An unsuccessful retry may be followed by another retry of that same
oldest failure. Retry `attempt` values increase for that failed operation in observation order.
Operations with a different fingerprint never resolve it.

This rule is intentionally direct rather than transitive. For example, with adjacent scheduled
occurrences `[2, 3]`, occurrence 3 may be both a retry of occurrence 2 and a newly faulted
operation. A later success resolves occurrence 2 only; occurrence 3 still requires its own later
successful linked retry.

Every fault-related `OPERATION_FAILED` event creates one required recovery-evidence row. Rows are
ordered by the recorder sequence of their failure events. A resolved row contains the successful
retry operation ID and recovery latency; an unresolved row contains `null` for both. Recovery
latency is the non-negative elapsed time from that failure event to its linked successful
`OPERATION_SUCCEEDED` event.

Retry evidence remains a deterministic black-box heuristic. Agent Chaos does not infer retry
intent, validate an internal retry policy, interpret workload logs, or prove semantic task
completion.

## Events

The schema-1 event envelope and all payload models remain exact. No scheduled-occurrence field or
new event family is added.

Each selected operation emits the existing sequence beginning with:

1. `OPERATION_OBSERVED`;
2. `RETRY_OBSERVED` when it is also a retry of an unresolved failure;
3. `FAULT_INJECTED`; and
4. exactly the existing terminal success or failure evidence required by that fault's behavior.

`FAULT_INJECTED` is emitted once per selected occurrence with the existing `operation_id`,
`fault_type`, and fault-specific `parameters`. Repetition is how schema-1 events represent a
schedule. Existing single-occurrence event streams remain valid and unchanged.

## Outcomes and reason codes

Results continue to be derived exclusively from the structured event stream. Existing
higher-precedence setup and execution results remain authoritative in this order: recorded run
error, missing workload completion, interruption, workload timeout, and workload exit-code
mismatch. After those checks:

- No configured fault and the expected workload exit produces
  `PASSED / BASELINE_SUCCEEDED`.
- A configured fault with zero injections produces `FAILED / FAULT_NOT_TRIGGERED`.
- A schedule with at least one but fewer than all configured injections produces
  `FAILED / FAULT_SCHEDULE_INCOMPLETE`, regardless of recovery from the injections that did occur.
- More injections than configured, duplicate selection of a scheduled ordinal, or other internally
  inconsistent schedule evidence produces `FAILED / INTERNAL_ERROR`.
- A complete schedule with no fault-related failed operation produces
  `PASSED / FAULT_TOLERATED`.
- A complete schedule with one or more fault-related failures, all resolved by successful linked
  retries, produces `RECOVERED / RECOVERY_OBSERVED`.
- A complete schedule with any unresolved fault-related failure produces
  `FAILED / RECOVERY_NOT_OBSERVED`.

Mixed tolerated and failed injections are classified by the failed injections: the result is
`RECOVERED` when every required recovery succeeds and `FAILED` when any remains unresolved.
Diagnostics for incomplete schedules state the configured and completed injection counts;
diagnostics for missing recovery state the required and successful recovery counts. They must not
include sensitive dependency traffic.

## Schema-2 reports

All v0.4 runs write a strict schema-2 report. Top-level identity, result, duration, operation
metrics, workload exit code, timing, artifacts, and diagnostics retain their v1 names and
meanings. `faults_injected` is the total number of `FAULT_INJECTED` events.

The schema-2 fault object is:

```json
{
  "configured": true,
  "type": "http_error",
  "injected": true,
  "scheduled_occurrences": [2, 4],
  "completed_occurrences": [2, 4],
  "schedule_completed": true
}
```

- `scheduled_occurrences` is the normalized configured schedule; it is empty for a baseline.
- `completed_occurrences` contains the scheduled ordinals that injected, in schedule order. It is
  empty when no injection occurred and otherwise is a prefix of `scheduled_occurrences`.
- `schedule_completed` is true when `completed_occurrences` equals `scheduled_occurrences`,
  including the empty baseline schedule.
- `injected` remains the compatibility convenience boolean equivalent to
  `bool(completed_occurrences)`.
- For a baseline, `configured` is false, `type` is null, both occurrence lists are empty,
  `schedule_completed` is true, and `injected` is false.
- For a configured fault, `type` is non-null and `scheduled_occurrences` is non-empty.
  `faults_injected` normally equals the length of `completed_occurrences`; the sole exception is
  an over-injection report with `FAILED / INTERNAL_ERROR`, where the top-level count preserves the
  excess evidence and may exceed the completed schedule prefix.

The schema-2 recovery object is:

```json
{
  "required": 2,
  "successful": 1,
  "evidence": [
    {
      "failed_operation_id": "<uuid>",
      "retry_operation_id": "<uuid>",
      "recovery_latency_ms": 25
    },
    {
      "failed_operation_id": "<uuid>",
      "retry_operation_id": null,
      "recovery_latency_ms": null
    }
  ]
}
```

- `required` equals the number of evidence rows and fault-related failed operations.
- `successful` equals the number of rows with a successful retry operation ID.
- `failed_operation_id` is always present and unique within the list.
- `retry_operation_id` identifies the linked successful operation or is null.
- A successful retry operation ID appears in at most one row.
- `recovery_latency_ms` is present exactly when `retry_operation_id` is present and is
  otherwise null.
- Baseline and fully tolerated runs use zero counts and an empty evidence list.

The v1 scalar recovery object is not embedded in a v2 report. Report versions are strict: fields
from one version cannot be mixed into the other, and unknown fields remain invalid.

## Inspection and CLI summary

`agentchaos inspect` accepts a strict schema-1 or schema-2 report from either a run directory or a
direct report path. It remains read-only, performs no migration, reads no companion artifact, and
returns exit 0 for any valid report regardless of experiment result.

Schema-1 reports use the exact existing summary, including `Successful recovery: yes|no`.
Schema-2 live and inspected summaries render schedule and recovery completion as
observed/required counts:

```text
Faults injected:       <completed>/<scheduled>
Successful recoveries: <successful>/<required>
```

The existing result, reason, failed-operation count, retry count, duration, and resolved
report-path lines retain their wording and ordering. Summary output does not print operation IDs,
evidence rows, diagnostics, event payloads, scenarios, or logs.

Existing inspection exit codes remain unchanged: 0 for a valid displayed report, 2 for invalid or
unreadable input, 3 for an unexpected internal failure, and 130 for interruption.

## Reports, artifacts, and safety

- Artifact filenames and relative references remain unchanged.
- `scenario.yaml` remains an exact copy of the supplied scenario, including scalar trigger syntax.
- `events.jsonl` remains schema 1 and is flushed according to the existing durability contract.
- Workload and managed-dependency logs remain verbatim subprocess output.
- v1 reports remain byte-for-byte unchanged during inspection.

Agent Chaos-generated events, reports, diagnostics, and terminal lifecycle messages must not
persist or display request or response headers, request or response bodies, raw query values,
environment values, URL user information, credentials, authorization data, or unsafe exception
text. Persisted HTTP evidence remains limited to the existing safe fields, hashes, identifiers,
integer occurrence ordinals, counts, and elapsed durations. User-authored scenario and subprocess
output retain the existing user responsibility described by prior specifications.

## Example scenarios

v0.4 adds two deterministic offline examples while retaining all ten v0.1 through v0.3 examples
with unchanged scenarios, results, event behavior, and CLI exit codes.

### `api_503_schedule_recovery.yaml`

- Uses `http_error` status 503 with `occurrences: [2, 4]`.
- The demo workload performs two refresh cycles. Each selected request fails, an identical retry
  succeeds, and the workload exits 0.
- Expected evidence: two injections, two fault-related failures, two separately linked successful
  retries, and two recovery-evidence rows.
- Expected result: `RECOVERED / RECOVERY_OBSERVED`.
- Expected CLI exit: 0.

### `api_503_schedule_incomplete.yaml`

- Uses `http_error` status 503 with a two-entry schedule whose second ordinal is not reached before
  the workload exits with its expected code.
- The first injection has a successful linked retry, demonstrating that partial recovery does not
  satisfy schedule completion.
- Expected evidence: one injection, one successful recovery-evidence row, and an incomplete
  two-entry schedule.
- Expected result: `FAILED / FAULT_SCHEDULE_INCOMPLETE`.
- Expected CLI exit: 1.

The examples use new loopback ports and require no network access outside the local machine.
The demo workload may gain opt-in configuration for repeated refresh cycles, but default behavior
must preserve every released example.

## Verification contract

Configuration and trigger coverage must include:

- acceptance of scalar `occurrence` and singleton or plural `occurrences` for all five fault types;
- rejection of missing, mixed, empty, duplicate, non-increasing, non-positive, boolean, fractional,
  and unknown trigger values;
- preservation of v0.1 through v0.3 parsing and normalization;
- exact selection of every configured occurrence and no unconfigured occurrence;
- retries participating in schedule counting; and
- concurrency-safe assignment matching eligible `OPERATION_OBSERVED` recorder order.

Proxy and event coverage must include:

- repeated injection with unchanged per-fault wire behavior and event payloads;
- exact per-operation ordering, including a retry that is itself injected;
- per-fingerprint FIFO queues with no cross-fingerprint correlation;
- failed retries remaining linked to the oldest unresolved failure;
- each success resolving at most one failure;
- adjacent scheduled occurrences requiring separate later successes;
- independent concurrent recovery chains without overwritten state; and
- unchanged schema-1 event validation and safe-data guarantees.

Analyzer, report, and CLI coverage must include:

- every precedence path, including zero, partial, exact, and over-injection schedules;
- fully tolerated, fully recovered, mixed tolerated-and-recovered, and partially recovered runs;
- deterministic evidence-row ordering, counts, IDs, nullability, and latency;
- strict schema-2 report validation and rejection of mixed or unknown fields;
- all v0.4 runs, including baselines and scalar scenarios, producing v2 reports;
- strict inspection of representative v1 and v2 reports without artifact mutation;
- byte-for-byte preservation of the v1 summary and exact v2 count summary;
- unchanged run and inspection exit meanings; and
- absence of sensitive traffic and unsafe errors from generated artifacts and output.

End-to-end coverage must include:

- all ten released examples with unchanged results and exit codes;
- plural schedule recovery with two injections and two successful evidence rows;
- a partially completed schedule failing even when every observed failure recovered;
- a complete schedule with an unrecovered failure;
- inspection of newly produced v2 successful and failed reports; and
- inspection of retained v1 report fixtures.

The release must pass the repository's full locked quality gate on supported Linux and
macOS/Python combinations without adding a production dependency.

## Explicit non-goals

v0.4 does not add:

- more than one fault configuration, per-occurrence fault parameters, ordered multi-fault
  campaigns, suites, or campaign aggregation;
- schedule windows, time-based triggers, durations, intervals, random or probabilistic selection,
  seeds, or replay commands;
- multiple dependencies, non-HTTP adapters, remote execution, or broader platform support;
- new fault types or changes to existing fault wire behavior;
- streaming responses, partial-response injection, SSE, WebSockets, CONNECT, or TLS interception;
- semantic task grading, workload-log interpretation, LLM-based recovery judgment, or automatic
  retry-policy validation;
- a new event family, event payload field, CLI command, artifact filename, alternate inspection
  format, report migration, or report editing; or
- a public fault, trigger, executor, proxy-protocol, or recovery-analyzer plugin API.

All remaining v0.1 through v0.3 limitations continue unless explicitly changed above.
