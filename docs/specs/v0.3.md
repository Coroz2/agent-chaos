# Agent Chaos v0.3 Specification

**Status:** Released

**Release:** `v0.3.0`

**Distribution:** `agent-chaos-runner==0.3.0`

This document is the authoritative contract for Agent Chaos v0.3. Released specifications are
immutable historical records. Changes are limited to clearly labeled factual corrections or
errata and must not introduce behavior that was not part of v0.3.

## Product contract

Agent Chaos v0.3 adds deterministic HTTP connection-disruption testing through one new fault,
`http_disconnect`.

The selected request is terminated by the Agent Chaos proxy before the workload receives a
complete HTTP response, and the request is never sent to the configured upstream. This gives a
workload a reproducible opportunity to retry after a client-visible transport or protocol failure.

The v0.2 execution model remains unchanged: one subprocess workload, one HTTP dependency, zero or
one fault, occurrence-based triggering, structured evidence, and no LLM-based recovery judgment.

## Compatibility contract

- Scenario, event, and report envelopes remain `schema_version: 1`.
- Every scenario valid under v0.1 or v0.2 remains valid under v0.3 with the same observable
  behavior.
- v0.3 adds `http_disconnect` to the schema-1 fault discriminator union. Earlier binaries are not
  required to accept scenarios or events containing the new value.
- v0.3 reads v0.1 and v0.2 reports without migration.
- `report.json` retains exactly the v0.1 field structure. No field is added, removed, renamed, or
  reinterpreted.
- Existing event types and payload fields remain unchanged. The new fault uses existing event
  families.
- Existing reason codes, analyzer precedence, artifact names, CLI commands, CLI output, and exit
  meanings remain unchanged.
- The wire behavior, triggering, events, outcomes, reports, and cleanup behavior of
  `http_latency`, `http_error`, `http_rate_limit`, and `http_malformed_json` remain unchanged.
- No production dependency or supported-platform change is introduced.

## Scenario contract

All v0.1 and v0.2 validation and normalization rules continue to apply. Fault models remain strict
discriminated mappings, reject unknown fields, and cannot mix fault-specific fields.

```yaml
fault:
  type: http_disconnect
  target:
    method: GET
    path: /customer/*
  trigger:
    occurrence: 2
```

Contract:

- `type` is exactly `http_disconnect`; aliases or shorter spellings are invalid.
- `target` and `trigger` use the existing schema-1 HTTP target and occurrence-trigger contracts.
- No fault-specific configuration fields are accepted.
- The scenario still contains at most one fault.
- Unknown fields and fields belonging to any other fault type are rejected.

## HTTP disconnect behavior

On the selected matching occurrence, the proxy:

1. buffers and identifies the request using the existing proxy path;
2. records the fault injection and failed-operation evidence defined below;
3. does not contact or forward any part of the request to the upstream; and
4. aborts the client connection before sending a complete HTTP response.

The portable public guarantee is that a conforming HTTP client cannot receive a complete HTTP
response for the selected request and observes the failure through its transport or HTTP-protocol
error path. Agent Chaos does not guarantee:

- a TCP RST packet rather than another abrupt connection termination;
- a particular operating-system socket error;
- a particular exception class, message, or retry classification from an HTTP client library; or
- any response status, headers, or body for the disconnected operation.

The disconnect is an internal proxy disposition alongside forwarding, fixed synthetic responses,
and abandonment. It must use the active inbound connection associated with the selected request.
Expected disconnect injection must not depend on deliberately invalid ASGI messages, an uncaught
application exception, or introspection of private bound-method internals, and it must not produce
an expected server traceback. Any inert response used only to complete internal ASGI bookkeeping
is not a client-visible response or public contract.

The existing concurrency-safe occurrence counter and at-most-once injection rule remain
authoritative. Under concurrent matching requests, exactly the configured occurrence is selected;
the selected connection is disrupted once, and non-selected requests retain ordinary behavior.

## Events, failure, and recovery

The selected operation uses the existing event envelope and begins with this exact event order:

1. `OPERATION_OBSERVED`
2. `FAULT_INJECTED`
3. `OPERATION_FAILED`

`FAULT_INJECTED`:

```json
{
  "kind": "FAULT_INJECTED",
  "operation_id": "<uuid>",
  "fault_type": "http_disconnect",
  "parameters": {}
}
```

`OPERATION_FAILED`:

```json
{
  "kind": "OPERATION_FAILED",
  "operation_id": "<uuid>",
  "fingerprint": "<sha256>",
  "failure_kind": "injected_disconnect",
  "status_code": null,
  "fault_related": true
}
```

Both evidence events must be durably recorded before the proxy aborts the client connection. The
selected operation does not emit `OPERATION_SUCCEEDED`, and the proxy does not additionally
classify the deliberate connection termination as `client_disconnected`, `proxy_error`, or an
upstream failure.

The fault uses the existing deterministic fingerprint of uppercase method, concrete path, query
hash, and body hash. On a later matching request, existing retry evidence applies:

1. `OPERATION_OBSERVED`
2. `RETRY_OBSERVED`, linked to the disconnected operation
3. `OPERATION_SUCCEEDED` if the retry receives an upstream status below 400

Existing analyzer precedence remains authoritative:

- Expected workload exit plus no injection: `FAILED / FAULT_NOT_TRIGGERED`.
- Expected workload exit plus injection but no successful fingerprint-matched retry:
  `FAILED / RECOVERY_NOT_OBSERVED`.
- Expected workload exit plus a linked retry that succeeds with status below 400:
  `RECOVERED / RECOVERY_OBSERVED`.
- Unexpected workload exit, timeout, interruption, setup error, or internal error retains its
  existing higher-precedence result and reason.
- `FAULT_TOLERATED` is not available because the proxy records a fault-related failed operation.
- Recovery latency remains the elapsed time between the injected `OPERATION_FAILED` event and the
  linked retry's `OPERATION_SUCCEEDED` event.

Retry evidence remains a deterministic black-box heuristic. Agent Chaos does not infer why the
client retried, require a particular client exception, or prove that the workload completed its
semantic task.

## Reports and artifacts

- `report.json` remains strict `schema_version: 1` with the exact existing structure.
- A new run may use `fault.type: http_disconnect` without changing `FaultReport`.
- No new report metric, recovery field, diagnostic category, or reason code is introduced.
- v0.1, v0.2, and v0.3 reports remain compatible at the report-model level because `fault.type`
  is already a nullable string.
- Artifact filenames and relative references remain unchanged.
- `scenario.yaml` remains an exact copy of the supplied scenario.
- Workload and managed-dependency logs remain verbatim subprocess output.

Existing safe-artifact rules continue to apply. Agent Chaos-generated events, reports,
diagnostics, and terminal lifecycle messages must not persist or display request or response
headers, request or response bodies, raw query values, environment values, URL user information,
credentials, or authorization data. Disconnect errors must be reduced to safe phase-specific
descriptions and exception types when raw exception text could expose dependency traffic or
credentials. Persisted HTTP evidence remains limited to the existing safe fields and hashes.

## Example scenarios

v0.3 adds two deterministic offline examples while retaining all eight v0.1 and v0.2 examples
unchanged.

### `http_disconnect_recovery.yaml`

- Targets the second `GET /customer/*`.
- Uses `http_disconnect`.
- The demo workload treats an HTTP client transport error as retryable, retries the identical
  request, receives a successful upstream response, and exits 0.
- Expected evidence: one injection, one fault-related failure, one linked retry, and a successful
  retry operation.
- Expected result: `RECOVERED / RECOVERY_OBSERVED`.
- Expected CLI exit: 0.

### `http_disconnect_failure.yaml`

- Targets the second `GET /customer/*`.
- Uses `http_disconnect` with the demo workload limited to one attempt.
- The workload receives the connection failure, does not retry, and exits with its configured
  expected exit code.
- Expected evidence: one injection, one fault-related failure, and no retry.
- Expected result: `FAILED / RECOVERY_NOT_OBSERVED`.
- Expected CLI exit: 1.

The examples use a new loopback port and require no network access outside the local machine.
Changes to the demo workload must not alter the results or exit codes of any existing example.

## Verification contract

Unit and proxy coverage must include:

- acceptance of the exact `http_disconnect` YAML contract;
- rejection of aliases, mixed fault fields, and unknown fault fields;
- preservation of all v0.1 and v0.2 scenario parsing and normalization;
- typed validation of `http_disconnect` fault events;
- exhaustive internal executor dispatch across all five HTTP fault types;
- exact fault parameters, failure payload, and event ordering;
- durable failure evidence before connection termination;
- absence of `OPERATION_SUCCEEDED` for the disconnected operation;
- a real HTTP client observing a transport- or protocol-level failure without requiring a
  particular exception subclass, error message, or TCP packet flag;
- confirmation that the selected request never contacts upstream;
- ordinary forwarding for non-selected requests;
- a successful fingerprint-matched retry and the existing recovery evidence chain;
- occurrence counting and exactly-once injection under concurrency;
- unchanged behavior for all four existing HTTP fault types;
- recovered, unrecovered, and higher-precedence analyzer paths;
- parsing representative v0.1, v0.2, and v0.3 reports without migration;
- report shape equality with the schema-1 report contract; and
- absence of raw headers, bodies, queries, environment values, URL credentials, authorization
  data, and unsafe exception text from Agent Chaos-generated evidence.

End-to-end coverage must include:

- all eight existing examples with unchanged results and CLI exit codes;
- disconnect recovery with one injection, one failed operation, one linked successful retry, and
  `RECOVERED / RECOVERY_OBSERVED`;
- managed disconnect without a retry producing `FAILED / RECOVERY_NOT_OBSERVED`; and
- successful inspection of reports produced by both new scenarios using the unchanged inspection
  contract.

The release must pass the repository's full locked quality gate on supported Linux and
macOS/Python combinations without adding a production dependency. Tests must assert portable
client-visible behavior and must not depend on platform-specific TCP reset details.

## Explicit non-goals

v0.3 does not add:

- configurable disconnect timing, response prefixes, transport flags, or other fault-specific
  parameters;
- a guarantee of TCP RST, a particular socket errno, or an exact client-library exception;
- upstream contact, response capture, or response mutation for the disconnected request;
- a public fault plugin, executor, proxy-protocol, or transport-abort API;
- automatic validation or configuration of workload retry policies;
- streaming response faults, partial response injection, SSE, WebSockets, CONNECT, or TLS
  interception;
- multiple dependencies, multiple faults, schedules, windows, probabilistic triggers, suites, or
  campaigns;
- MCP or any other non-HTTP dependency adapter;
- remote execution, broader platform support, semantic task grading, or LLM-based recovery
  judgment; or
- a new report schema, event family, reason code, CLI command, or inspection format.

All remaining v0.1 and v0.2 limitations continue unless explicitly changed above.
