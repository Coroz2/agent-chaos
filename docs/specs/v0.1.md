# Agent Chaos v0.1 Specification

**Status:** Released  
**Release:** `v0.1.0`  
**Distribution:** `agent-chaos-runner==0.1.0`

This document is the authoritative contract for Agent Chaos v0.1. Released specifications are
immutable historical records. Changes are limited to clearly labeled factual corrections or
errata and must not introduce behavior that was not part of v0.1.

## Product contract

Agent Chaos v0.1 is a local and CI-friendly chaos runner for agent developers. It launches an
opaque subprocess workload, routes one HTTP dependency through a loopback reverse proxy, injects
zero or one deterministic fault, records a structured event stream, and reports whether the
workload passed, recovered, or failed.

The core is independent of model vendors and agent frameworks. v0.1 does not require an OpenAI,
Anthropic, or other paid API key.

## Package and platform contract

- Product name: **Agent Chaos**.
- Python distribution: `agent-chaos-runner`.

## Scenario contract

Scenarios are strict YAML mappings validated by Pydantic. Unknown fields are rejected. Commands
are argument lists executed directly without a shell. Relative working directories resolve from
the scenario file's directory.

```yaml
schema_version: 1
name: api-503-recovery

dependency:
  type: http
  base_url: http://127.0.0.1:19103
  start:
    command: [python, fake_api.py, --port, "19103"]
    cwd: ..
    env: {}
    readiness:
      path: /health
      timeout_seconds: 5

workload:
  name: demo-agent
  command: [python, demo_agent.py]
  cwd: ..
  env: {}
  proxy_url_env: CUSTOMER_API_URL

fault:
  type: http_error
  target:
    method: GET
    path: /customer/*
  trigger:
    occurrence: 2
  status_code: 503

success:
  exit_code: 0

timeout_seconds: 10
```

### Top-level fields

- `schema_version` is exactly `1`.
- `name` is a non-empty experiment name.
- `dependency` defines exactly one HTTP or HTTPS upstream.
- `workload` defines exactly one subprocess workload.
- `fault` is optional and singular.
- `success.exit_code` is an integer from 0 through 255.
- `timeout_seconds` is positive and defaults to 60.

### Commands and environments

- Dependency and workload `command` values contain at least one non-empty argument.
- Commands execute with the parent environment plus scenario overrides.
- `cwd` is optional and resolves relative to the scenario file; omission uses the scenario
  directory.
- Workloads always receive `AGENTCHAOS_PROXY_URL` and `AGENTCHAOS_RUN_ID`.
- When `workload.proxy_url_env` is configured, it must be a valid environment-variable name and
  receives the same proxy URL.

### Dependency startup

Managed startup is optional. When `dependency.start` is present, Agent Chaos launches the command
before the proxy and requires a readiness endpoint:

- the readiness path begins with `/`;
- `timeout_seconds` is positive and defaults to 5;
- readiness succeeds on an HTTP status from 200 through 399;
- readiness fails if the dependency exits first or does not become ready before the timeout.

When startup is omitted, the configured upstream must already be available.

### Fault targets and triggers

- The optional target method is normalized to uppercase.
- The path is case-sensitive, begins with `/`, and supports only `*` as a wildcard.
- Query parameters do not participate in target matching.
- `trigger.occurrence` is a positive integer.
- Matching-request counting is concurrency-safe and the configured fault injects exactly once.

### Supported faults

- `http_latency` requires a positive integer `latency_ms`.
- `http_error` requires a `status_code` from 400 through 599.
- Fault-specific fields cannot be mixed because the fault union is discriminated by `type` and
  all models reject unknown fields.

## CLI contract

```text
agentchaos run <scenario> [--output-dir PATH]
agentchaos validate <scenario>
agentchaos version
agentchaos --version
```

- `run` validates the scenario, streams selected lifecycle events and prefixed workload output,
  prints a result summary, and writes a run directory.
- The default output root is `.agentchaos/runs`.
- `validate` parses and validates without launching a dependency, proxy, or workload.
- Both version commands print `agentchaos <version>`.
- Completion generation is disabled and invoking the CLI without a command shows help.

### Exit codes

- `0`: experiment result is `PASSED` or `RECOVERED`, or a non-run informational command succeeds.
- `1`: a valid experiment completes with result `FAILED`.
- `2`: scenario or command usage is invalid.
- `3`: dependency, proxy, workload setup, or an internal run failure prevents normal execution.
- `130`: execution is interrupted.

## HTTP proxy contract

The reverse proxy binds to an ephemeral port on `127.0.0.1` and forwards supported ordinary HTTP
methods to one configured HTTP or HTTPS upstream.

- Requests and responses are buffered up to 10 MiB.
- Oversized request bodies return 413; oversized upstream bodies return 502.
- Hop-by-hop, host, and content-length headers are not forwarded as end-to-end headers.
- Redirects are returned to the workload and are not followed by the proxy.
- Ambient proxy environment variables are ignored for upstream and readiness traffic.
- Upstream HTTP transport failures return a sanitized 502 response.

An injected HTTP error returns deterministic JSON with `X-Agent-Chaos-Fault: http_error` and does
not contact the upstream. Injected latency waits for the configured duration unless a matching
retry or client disconnect shows that the original request was abandoned; abandoned requests do
not continue to the upstream.

## Events

Each line of `events.jsonl` is a strict event object with this versioned envelope:

```text
schema_version: 1
event_id: UUID string
run_id: run identifier
sequence: positive recorder-assigned integer
timestamp: UTC timestamp
elapsed_ms: non-negative integer
type: event type
component: emitting component
payload: type-specific strict object
```

The recorder serializes concurrent emissions under a lock, assigns authoritative sequence
numbers, appends one JSON object per line, and flushes every event immediately.

### Event families

- Run: `RUN_STARTED`, `RUN_ERROR`, `RUN_COMPLETED`.
- Dependency: `DEPENDENCY_STARTED`, `DEPENDENCY_READY`, `DEPENDENCY_STOPPED`.
- Injector: `INJECTOR_STARTED`, `FAULT_INJECTED`.
- Workload: `WORKLOAD_STARTED`, `WORKLOAD_COMPLETED`.
- Operation: `OPERATION_OBSERVED`, `OPERATION_FAILED`, `RETRY_OBSERVED`,
  `OPERATION_SUCCEEDED`.

The event `type` must match the payload discriminator `kind`. Operation events use operation IDs
and a fingerprint derived from the uppercase method, concrete path, SHA-256 query hash, and
SHA-256 body hash.

### Safe-data rules

Persisted HTTP evidence is limited to method, concrete path, status, duration, identifiers, fault
parameters, and correlation hashes. Events and reports do not persist:

- request or response headers;
- request or response bodies;
- raw query values;
- credentials or authorization data.

## Recovery and outcomes

Metrics and outcomes are derived exclusively from the structured event stream. Workload log text
and LLM judgment do not affect classification.

- `PASSED` with `BASELINE_SUCCEEDED`: no fault is configured and the workload exits as expected.
- `PASSED` with `FAULT_TOLERATED`: a fault is injected but no fault-related failed operation is
  observed, such as latency tolerated within the workload timeout.
- `RECOVERED` with `RECOVERY_OBSERVED`: a fault-related operation fails, a later request has the
  same fingerprint, the retry is linked to the failed operation, the retry succeeds, and the
  workload exits as expected.
- `FAILED`: setup or execution fails, the expected workload exit code is not observed, the fault
  does not trigger, or successful recovery is not observed.

Primary failure reason codes are:

- `DEPENDENCY_START_FAILED`;
- `PROXY_START_FAILED`;
- `WORKLOAD_SPAWN_FAILED`;
- `INTERNAL_ERROR`;
- `WORKLOAD_NOT_COMPLETED`;
- `INTERRUPTED`;
- `WORKLOAD_TIMED_OUT`;
- `WORKLOAD_EXIT_CODE_MISMATCH`;
- `FAULT_NOT_TRIGGERED`;
- `RECOVERY_NOT_OBSERVED`.

Reason precedence follows the analyzer order: run errors, missing completion, interruption,
timeout, exit-code mismatch, baseline success, missing injection, tolerated fault, then recovery
analysis. Retry classification is deterministic black-box evidence, not proof of workload intent.

## Report and artifacts

Every valid run creates a unique directory under the selected output root:

```text
<run-id>/
├── scenario.yaml
├── events.jsonl
├── stdout.log
├── stderr.log
├── dependency.stdout.log
├── dependency.stderr.log
└── report.json
```

Dependency logs exist only for a managed dependency. The scenario file is copied as the run
snapshot. Workload and dependency output is written to raw log files; workload output is also
streamed to the terminal with a label and channel prefix.

`report.json` is written atomically and uses strict `schema_version: 1`. Its top level contains:

- identity and outcome fields: `run_id`, `scenario_name`, `result`, `reason_code`, and
  `duration_ms`;
- common metrics: `faults_injected`, `operations_observed`, `successful_operations`,
  `failed_operations`, `retries_observed`, and `workload_exit_code`;
- nested `workload`, `fault`, `recovery`, `timing`, and `artifacts` objects;
- a `diagnostics` list for concise run explanations.

Recovery details identify the failed and retry operation IDs and recovery latency when recovery is
observed. Artifact references are paths relative to the run directory.

## Process lifecycle and cleanup

- Subprocesses start without a shell, with stdin disconnected and stdout/stderr captured.
- Each process starts in its own POSIX session/process group.
- Timeouts and cleanup send `SIGTERM`, wait up to two seconds, then send `SIGKILL` if necessary.
- Proxy and managed dependency cleanup runs even after setup or workload failures.
- Dependency stop, run completion, and the final report are recorded whenever the run directory
  was successfully created and the orchestrator can finalize normally.

## Demonstration scenarios

v0.1 ships deterministic offline examples for:

- `no_fault.yaml`: baseline `PASSED`;
- `api_latency_recovery.yaml`: latency `RECOVERED`;
- `api_503_recovery.yaml`: synthetic 503 `RECOVERED`;
- `api_503_failure.yaml`: no-retry workload `FAILED`.

The fake API provides health, customer, and order endpoints. The demo workload uses fixed retry
behavior and does not require network access outside the local machine.

## Quality contract

The v0.1 release is covered by configuration, trigger, proxy, event, analyzer, reporting, CLI, and
real subprocess/socket integration tests. CI runs:

- pytest, Ruff, formatting, and mypy on Linux Python 3.12 through 3.14;
- package construction and strict metadata/archive checks on Linux;
- a representative macOS integration smoke test;
- an installed-wheel validation and recovery scenario during release.

## Explicit v0.1 limitations

- One workload, one HTTP dependency, and zero or one fault per scenario.
- Workloads must accept a dependency base URL through environment configuration.
- No transparent system-wide interception or TLS man-in-the-middle support.
- No streaming responses, SSE, WebSockets, or CONNECT tunneling.
- No multiple simultaneous faults, fault schedules, or probabilistic triggers.
- No non-HTTP dependency adapters, Docker runner, Python-callable runner, or remote runner.
- No model-specific integrations, semantic task grading, suites, comparisons, or benchmarks.
- No official Windows support.

Future versions may address these limitations only through a new approved specification; they do
not alter this released v0.1 record.
